API v1 · JSON · HTTPS

API mobile EVENT TRANS

Toutes les fonctions des trois applications mobiles : spectateur (acheter, montrer et suivre son Pass), convoyeur (contrôler les Pass, même sans réseau, et conduire la mission) et service technique (prendre en charge les pannes).

URL de basehttps://<domaine>/api/v1Recette et production : adresses communiquées par ACCES EVENT. En local : http://localhost:8000/api/v1.
Formatapplication/jsonToujours envoyer Accept: application/json. Dates ISO 8601 avec fuseau ; montants en FCFA entiers.
LanguefrLes champs message et *_label sont prêts à afficher.

Les exemples de cette page sont de vraies réponses de l'API, obtenues sur le jeu de démonstration le 13/11/2026. Les listes longues sont raccourcies (// … autres) et les jetons masqués. La référence technique générée automatiquement reste disponible sur /docs/api.

Authentification

Pas de mot de passe : chacun se connecte avec son numéro de téléphone et un code à 6 chiffres reçu par SMS. Le code est valable 5 minutes, 5 essais au plus ; un nouveau code peut être demandé après 60 secondes.

  1. POST /auth/otp avec le numéro et le type de compte : customer (spectateur) ou staff (convoyeur, technicien).
  2. POST /auth/verify avec le code : la réponse donne un jeton à conserver dans le stockage sécurisé du téléphone (Keychain, Keystore).
  3. Chaque appel envoie Authorization: Bearer <jeton>. Le jeton n'expire pas ; POST /auth/logout le révoque.

Le jeton porte une capacité selon le profil : customer, conveyor ou tech. Un jeton ne donne accès qu'aux appels de son application ; une réponse 401 ou 403 sans code métier signifie qu'il faut reconnecter l'utilisateur.

Pour le personnel, la demande de code répond toujours la même chose, que le numéro existe ou non : on ne révèle pas qui fait partie des équipes. Les chauffeurs n'ont pas d'accès mobile.

Réponses et erreurs

Une réponse réussie place ses données dans data. Une erreur a toujours un message lisible, à afficher tel quel :

  • Erreur métier : message + code stable. Testez le code, jamais le texte. Liste des codes.
  • Champ invalide (422) : message + errors, un tableau de messages par champ, à placer sous le champ concerné.
  • 401 non connecté · 403 pas le droit · 404 introuvable (ou pas à vous) · 429 trop de requêtes · 5xx réessayer plus tard.

Terminaux du personnel

Les applications convoyeur et technique envoient deux en-têtes en plus du jeton, sur tous leurs appels :

En-têteExempleRôle

Événements en vente

GET/eventsPublic

Événements ouverts à la vente sur l'application, les événements mis en avant d'abord, puis par date. from_price est le prix « dès » à afficher sur la carte ; communes_count, le nombre de communes desservies.

Détail d'un événement

GET/events/{id}Public

Tout ce qu'il faut pour l'écran « Choisir mon Pass » : points d'embarquement avec zone et heure de convocation, offres, grille de prix par zone, places restantes, zones de dépose, liens des CGV.

Prix d'un Pass : dans offers[].prices, la ligne dont la zone est celle du point choisi et le pass_type celui demandé. offers[].remaining donne les places restantes par type. Les frais de paiement (fee_rate, 2 %) s'ajoutent au total ; le plus simple est d'appeler le devis.

Payer

Lance le paiement. La réponse ne veut pas dire « payé » : la confirmation vient de l'agrégateur, côté serveur.

  • Mobile Money : afficher instructions.message (validation sur le téléphone), puis suivre la commande.
  • Carte : ouvrir instructions.redirect_url dans un navigateur intégré (3-D Secure).
ChampTypeDescription

Erreurs possibles

Suivre une commande

GET/orders/{reference}Spectateur

À interroger toutes les 3 secondes après le paiement (2 minutes au plus). Quand status vaut payee, les Pass sont émis : ouvrir « Mes Pass ». echouee : proposer un autre moyen de paiement. expiree : recommencer la réservation. a_rembourser : le paiement est arrivé trop tard et les places ont été revendues ; le spectateur est remboursé.

Détail d'un Pass

GET/passes/{code}Spectateur

Le Pass avec son QR, l'état de chaque trajet, ce que permet l'annulation (cancellation), le remboursement éventuel (refund) et la possibilité de donner son avis (review).

Affichez le bouton « Annuler mon Pass » seulement si cancellation.allowed ; sinon montrez cancellation.message. Le bouton « Donner mon avis » suit review.available.

Transfère le Pass à un autre numéro tant que l'aller n'est pas scanné. Le bénéficiaire le reçoit par SMS et WhatsApp ; l'ancien QR devient invalide (la version du jeton change) : retirez le Pass du stockage local.

ChampTypeDescription

Erreurs possibles

  • PASS_NOT_TRANSFERABLE Pass déjà utilisé à l'aller, annulé ou terminé.

Annuler et être remboursé

POST/passes/{code}/cancelSpectateur

Annule le Pass et lance le remboursement sur le moyen de paiement d'origine. Montrez d'abord les montants de cancellation et demandez confirmation.

  • Jusqu'à 24 h avant le départ aller, Pass non scanné : 8 % retenus (3 060 payés → 2 815 remboursés).
  • Événement reporté : remboursement intégral, sans frais.

refund.status : a_traiter puis rembourse. Le spectateur reçoit un SMS quand l'argent est renvoyé.

Erreurs possibles

  • PASS_NOT_CANCELLABLE Annulation impossible : déjà scanné, moins de 24 h avant le départ, ou déjà annulé. Le message dit pourquoi.

Historique et détail

GET/tech/interventionsTechnicien

Interventions de l'équipe, la plus récente d'abord. GET /tech/interventions/{id} donne le détail d'une intervention.

Parcours d'achat

  1. ChoisirGET /events/{id} puis POST /orders/quote à chaque changement.
  2. Se connecter si besoin : /auth/otp puis /auth/verify, en gardant la sélection.
  3. RéserverPOST /orders avec accept_terms: true. Les places sont bloquées 15 min : afficher le compte à rebours.
  4. PayerPOST /orders/{ref}/pay, puis afficher les instructions.
  5. Attendre la confirmationGET /orders/{ref} toutes les 3 s jusqu'à payee, echouee ou expiree.
  6. Enregistrer les PassGET /me/passes : stocker chaque qr_token pour l'affichage hors ligne.

Ne jamais considérer un paiement comme réussi à partir du retour de l'écran de paiement : seul le statut de la commande fait foi (webhook signé de l'agrégateur).

Contrôle hors ligne

L'app convoyeur doit tenir une journée entière sans réseau (NF-09).

  1. Avant le départ télécharger le manifeste de chaque mission du jour.
  2. Vérifier le QR sans réseau : signature Ed25519 avec public_key, puis Pass présent dans passes, version égale, absent de revoked, segment non encore utilisé sur ce terminal.
  3. Décider la couleur avec les mêmes règles qu'en ligne : vert, orange (autre bus prévu), rouge (motif).
  4. Mettre en file chaque scan avec un client_uuid et son heure.
  5. Synchroniser avec POST /scans/sync dès que le réseau revient ; les réponses font foi et signalent les conflits.

Format du QR

Le QR contient un jeton ET1.<données>.<signature>, en base64url :

CléContenu
pIdentifiant du Pass
eÉvénement
bPoint d'embarquement
oOffre
tType de Pass
vVersion : augmente quand le Pass est offert ; un QR d'une ancienne version est refusé.

La signature Ed25519 porte sur la chaîne ET1.<données>. Le spectateur affiche le qr_token tel quel ; le convoyeur peut aussi saisir le code lisible du Pass (ET-AAMM-NNNN-COM), vérifié en ligne.

Gestion d'une panne

  1. ConvoyeurPOST /breakdowns (ou SMS « PANNE » sans data). La mission passe en « Panne ».
  2. Techniciens des équipes mobilisées : notification push, alerte dans GET /tech/alerts.
  3. Une équipe prend l'alertePOST /tech/alerts/{id}/take, puis avance les étapes.
  4. Clôture réparé, remplacé ou remorquage. En cas de remplacement, une nouvelle mission apparaît chez le convoyeur avec le bus de réserve.
  5. Montée dans le bus de remplacement le convoyeur scanne les passagers : vert au premier scan de contrôle, rouge s'il est répété.
